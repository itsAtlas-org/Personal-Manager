# SYNC-SET.md — who owns each unit of truth

PM is local-first, and for a long time "the vault plus its rules file is the portable part" was a
good enough answer. It is no longer accurate. Several features since have chosen the **database**
as their home for truth — structured preferences, chat sessions, flag assertions, the activity
log, retrieval feedback — and a copy-the-Markdown-across model would strand every one of them on
one machine, silently, with no error and no empty state to notice.

This file fixes the answer per table, in advance of the work that will need it. It is **checked by
`just sync-set`**: every table the schema creates must appear below with a class, so a new table
cannot land unclassified.

Deciding this now is cheap — it is one row per table. Deciding it later means excavating
ownership out of a dozen shipped features while a sync implementation waits.

## Classes

| Class | Meaning | On a second device |
|---|---|---|
| **truth** | User-authored or user-owned meaning. Losing it is data loss; no process can recompute it. | Must arrive. |
| **derived** | Reconstructable from truth by a documented rebuild path. | Rebuilt locally, never shipped. |
| **device** | Genuinely about *this* machine — paths, hardware, per-device credentials, local spend. | Stays put. |
| **mixed** | Truth and non-truth in one table, split by column or key. The split is named in Notes. | Only the truth part travels. |

Two rules that fall out of the classes:

- **`derived` is a promise, not a label.** Marking a table derived asserts that a rebuild path
  exists *and is reachable from the UI*. If re-deriving costs a model call, say so in Notes — it
  is still derived, but the cost is a product decision, not a free lunch.
- **`device` is not "unimportant".** A device-local row often has a truth-shaped counterpart that
  does need to travel (a connector *account* is portable; its OAuth token is not). Notes name the
  counterpart.

## The register

| Table | Class | Notes |
|---|---|---|
| `documents` | truth | Filing is truth: `project` (the HOME project), `tags`, `importance`, `reviewed`, `entity_id`. Device-local columns: `source_path`, `vault_path`, `source_id` (a local connector row). The body is in the vault, not here. A document's *other* project memberships are in `document_tags`. |
| `document_locations` | device | Every PLACE a connector found a document's file, one row each (#710). Device, not truth, and the distinction is the point: a `source_id` names a Drive account, a shared-drive id or an absolute path on **this machine**, none of which mean anything on another one — a second device reaches the same file through its own accounts and its own folders, and re-derives its own rows on its first sync. What IS truth here is the FILING, and that already lives on `documents` and travels in the `.pmindex` manifest. The manifest carries the sibling locations anyway, as a hint rather than a promise: a restore that lands them keeps a fold intact, and a restore that doesn't simply re-offers the pair to the duplicate pass. |
| `tags` | derived | The tag registry, both kinds. Project rows are re-derived from the vault (`project:` + `linked_projects:` front-matter) and the index-only manifest; group rows from `documents.tags`, which is itself re-derived from the vault's `tags:` line. Nothing here is authored, and `ingest::rebuild` reconstructs all of it — no model call. |
| `document_tags` | derived | Which documents carry which tags — project membership and free-form labels alike. Same rebuild path as `tags`, from the same front-matter; `ingest::write_document_truth` is its only writer, so it cannot diverge from the vault it indexes. |
| `chunks` | derived | Rebuilt by `ingest::rebuild` from the vault body. For index-only rows the content is a placeholder summary — see INVARIANTS.md I-10. |
| `chunk_vec` | derived | Embeddings. Already has a rebuild-on-mismatch path via the retrieval config stamp. Never portable: dimension and model must match the local registry. |
| `chunks_fts` | derived | FTS5 index over chunk text. |
| `conversations` | truth | Chat titles and project scope. The turn text is authoritatively in the vault; this row is not recomputable from it alone. |
| `messages` | truth | Bodies mirror the vault, but `citations`, `retrieved_chunk_ids` and `model` exist only here. |
| `chat_sessions` | derived | Session↔document mapping, rolling summary, cursors, last prompt size. Re-derivable — but regenerating the summary is a **billable** model call. |
| `settings` | mixed | Key-namespaced grab-bag. Truth: user preferences (retrieval k, reranking, backup frequency/retention), the per-Google-account calendar editing choice (`calendar_editing`, keyed by account email; editing also needs the account's keychain token, so a restore onto another machine shows it as needing Google's permission until reconnected) and the three Google Contacts keys, each keyed by the lowercased account address like it (`contacts_sync`, `"once"` or `"live"`; `contacts_writing`, `"on"` or `"paused"`, which with a token holding the `contacts` scope is what lets PM send changes; `contacts_write_granted`, a list of the accounts that ever granted that scope). A restore brings them without the sign-in, so an account reads as needing Google's permission again until it is reconnected; none of them holds a token or a contact **and the three webview blobs that hold user content** — `milestone_ui` (the per-project milestone sort, keyed by PROJECT NAME, plus the show-completed toggle), `calendar_ui` (the hidden-calendar set, where a mod's calendar overlay is `mod:<id>` (the Pinboard's keeps its pre-mods `pm:pinboard`, so a saved set still applies) and an uninstall removes it, as does a backup's or export's copy for a developer's folder test mod, the last calendar an event was created in, whose ids are routinely the account's email address, and the Runway's named windows, `runway_windows`: user-written labels such as a trip, with their dates) and `backup_ui` (dismissed reconcile banners, keyed by destination + cloud account). Those three moved out of the webview's plaintext `localStorage` and are allowlisted to the webview in `settings.rs::WEBVIEW_PREFS`; they each get their own key because `project_ui` is rewritten whole on every divider drag. Truth too, briefly: `calendar_split_journal`, the record of a "this and following" calendar change from just before its first write until it's settled (Google calendar and event ids, which can hold the account's address, the original's repeat rules and start, and a plan digest; never a title or description). A `.pmbackup` carries it verbatim; PM reads Google again before acting on any entry, so a stale or restored one can only refuse a change until Google shows otherwise, and is never sent anywhere. Device: `mods_store_id`, the random name of this store's own mods folder on each machine (`data_dir/mods/<vault_id>/<store_id>/`), minted by its first install (or a startup that finds `mods` rows without one) and deleted by a restore, so a restored copy never shares a folder with the store it came from; a `.pmbackup` carries it, the restore drops it. Derived, two notes the mod safety list leaves for the Mods tab's strips (Mods spec §1.10): `mods_resumed` (a JSON array of `{id, version, at}`, the mods the blacklist turned back on, until the "X is back on" strip is dismissed) and `mods_updates_waiting` (a JSON object keyed by mod id, `{version, sha256, kind, widenings, needsApi}`, a background update that asks for more than was granted or needs a newer PM, until it is approved, superseded or the mod goes). Both read as none when unreadable (they are notes, not state), and the waiting one is rebuilt by the next fetch; a `.pmbackup` carries them verbatim, and a stale one is cleared by the install that catches up with it. Mixed, one note that is half device: `mods_disclaimer` (a JSON object `{"v": 1, "devices": ["<credential>", ...]}`, at most 32 entries, newest last), which devices have accepted the Mods disclaimer in this vault (Mods spec §1.13, plan decision 7: per device AND per vault). An entry is the hex SHA-256 of `"pm-mods-disclaimer-v1" || 0x00 || <device id>` (`tab::device::credential`), where the id is `data_dir/mods-device-id`'s random value (see "Beyond the database"): **the raw id is never in any row**, so a reader of a shared store can't lift it and write it somewhere that means something else, and developer mode's entries are made under another domain, so one record's value is no use in the other. A `.pmbackup` or a shared vault carries the list, but a new machine's credential isn't in it, so it asks again, and so does a vault that has never heard of this one. The first-open "Turn on" of an auto-installed mod writes it too (D17). Unreadable, not ours, or in the old raw-id form, it reads as nobody having accepted. Truth: `backup_mod_data` (`"true"`/`"false"`, on when absent), "Also save mod data in my backups": whether a backup snapshot keeps content-class `mod_kv` rows (the mods' own saved data); off, a restore brings those mods back empty, with one exception: if the Pinboard's board moved into its mod from PM, a backup taken with this off still holds that board as it was when it moved (the frozen `settings['pinboard']` row, copied back into the mod by the restore, below), and a store whose board never moved has no Pinboard board in such a backup at all. It is about what a `.pmbackup` carries, so the export (the user's own copy) keeps them whatever it says, and it travels in a `.pmbackup` like the schedule. Developer mode, per device AND per vault (`mods_dev_devices`: a JSON object `{"v": 1, "devices": ["<credential>", ...]}`, at most 32 entries, newest last; Mods spec §1.15, INVARIANTS.md I-34): which devices have it on in this vault, each entry the hex SHA-256 of `"pm-mods-dev-mode-v1" || 0x00 || <device id>` (`devmode::credential`; never the raw id, and not the disclaimer's value, so nothing read from the disclaimer's row switches it on). It decides whether an unsigned mod may be installed and run, so a `.pmbackup` or a shared vault carries the list but a restore writes an empty one (`devmode::all_devices_off`, which also turns the old row below off) and a new machine's id isn't in it: it starts off. Only Rust reads or writes it, and nothing but a record that lists the device ever switches it on: asking (`devmode::is_on`) writes only toward off, a vault with no record is off for every device, and a record that is deleted leaves everyone off. The record is only half the answer: the device keeps the other half in `data_dir/mods-dev-mode.json` (see "Beyond the database"), and developer mode is on only when both list this device in this vault, so a credential written back into the store after a switch-off or a restore switches nothing on. The old webview-written `dev_mode` row is no longer in the page's allow-list and is **never read by any code** (an earlier build carried an old "on" over to the first device that asked; that let anyone holding a shared store's key delete the record and write the old row to switch the victim's device on, so it is gone, and upgrading turns developer mode off once: it is switched on again in Settings > Developer). The one thing Rust does with the old row is write it `"false"` in the restore's reset, together with the empty record (`devmode::all_devices_off`, `backup::adopt_mods`; so an older PM sharing the vault starts off too). A join of a shared vault writes nothing about it. Only `mods/devmode.rs` names the old row, and only for that write-off; `the_old_dev_mode_row_is_named_only_by_devmode_and_only_to_write_it_off` (in `backup/adopt_mods.rs`) fails when anything else names it or anything reads it. Unreadable, not ours, or in the old raw-id form, it reads as nobody being on. Local model scan dir, external CLI paths, sync cursors, last-run timestamps, the On battery policy (`local_llm_power_threshold`, `local_llm_power_roles`, `local_llm_power_cloud_consent`) and `local_llm_battery_idle_minutes` — about this machine's battery and consent to bill this device's key; a `.pmbackup` still carries them verbatim. Device, one class for every row that is about the providers a person reaches with their own key (opt-in per provider, off by default): `direct_openai_enabled` (`"true"` or absent), `chat_cloud_provider` and `background_cloud_provider` (`"openrouter"` or a direct provider's token; absent or unknown is OpenRouter), `direct_openai_chat_models` and `direct_openai_background_models` (a JSON array of PM's catalogue ids, one in this version), `direct_openai_chat_effort` and `direct_openai_background_effort` (a level or absent), `direct_openai_key_check` (JSON: the last key check's verdict, the catalogue ids the key could see and the count), `direct_openai_shares_data` (`"true"` or absent: the person's own tick-box that their project shares data, display only), the same rows for Google Gemini (`direct_gemini_enabled`, `direct_gemini_chat_models`, `direct_gemini_background_models`, `direct_gemini_chat_effort`, `direct_gemini_background_effort`, `direct_gemini_key_check`; Gemini has no tick-box, its tier is detected), the same six again for Anthropic less the tick-box (`direct_anthropic_enabled`, `direct_anthropic_chat_models`, `direct_anthropic_background_models`, `direct_anthropic_chat_effort`, `direct_anthropic_background_effort`, `direct_anthropic_key_check`; there is no `direct_anthropic_shares_data` and no tier) and `local_llm_power_cloud_consent_direct` (JSON `{"openai":"chat"|"background"|"both","gemini":...,"anthropic":...}`, the On battery consent for those providers, kept apart from OpenRouter's so a yes given for a zero-retention route never covers one that isn't). A key check's verdict (`direct_gemini_key_check` carries the key's tier, paid or free, and when a failed call said the project is free) is bound to ONE key by `key_fp`, a truncated SHA-256 stored with it and never sent to the webview: a carried verdict, free or paid, counts only beside a present key whose fingerprint matches, else it reads as no verdict (which reads as free), and a free verdict is re-read against THIS device's region at read, never stored as a block. A `.pmbackup` and a shared vault carry them verbatim, and they are never proof of anything on this device: the KEY is a keychain secret and travels nowhere. Restore and join deliberately KEEP them (no reset, unlike `mods_dev_devices`), because nothing leaves the machine without a key typed on THIS device. Three guards make the carried rows honest: a stored verdict is shown only beside a key that is present; a role stored on a direct provider that isn't opted in answers from OpenRouter (read-time demotion, reported as stored vs effective); and a role on a provider with no key here says so instead of failing quietly. The Local AI switch (`local_ai_enabled`, `"true"`/`"false"`), whether this machine runs a local model at all: written once at a store's first open from whether any Local AI setting was stored, then only by the switch; a `.pmbackup` carries it verbatim, so a restore onto a machine with no model server shows Local AI on until it is switched off. Beside it, `local_llm_chat_model_emptied` and `local_llm_background_model_emptied` (`"true"` or absent): switching Local AI off cleared that role's chosen local model, so it waits for a model rather than falling through to the cloud; written only by switching off, deleted when a model or a routing is chosen for the role, or by the Local AI tab's reset; a `.pmbackup` carries them verbatim. Retired: `voice_enabled`, the old voice-input switch (`"true"`/`"false"`). Voice input was removed until a better speech engine replaces it, so nothing reads or writes the key now, but a store an earlier PM opened still holds the row (left in place, inert) and a `.pmbackup` from one carries it verbatim. The key must never be reused: a future speech-to-text takes a new key, so an old row can't switch it on for someone who never chose it. Derived: the briefing cache, layout caches, the retrieval config stamp, the filing seed vocabulary (`filing_seed_vocabulary` — machine-guessed from the unreviewed backlog, regenerable, and travels verbatim in a `.pmbackup`), `calendar_default_length`, each Google account's default event length (minutes), keyed by account email and read from Google when an account connects and at each sync (a read that fails keeps the last value; a disconnect clears it); a `.pmbackup` carries it verbatim. `calendar_auto_meet`, each Google account's "Automatically add Google Meet video conferences to events I create" (true or false), keyed by account email and read from Google's settings list the same way (a read that fails keeps the last value; a disconnect clears it); a `.pmbackup` carries it verbatim. Truth, the pilots' auto-install (`mods/autoinstall.rs`; a mod PM moved out of core, the Map first): `mods_autoinstall_<pilot>` (`mods_autoinstall_map`, value `"1"`), a marker meaning "this store used the feature and is owed the mod". Migration v61 writes `mods_autoinstall_map` (`"1"`) when the store holds any document, and a restore writes it again when the restored store holds the pilot's signed catalogue row (`autoinstall::mark_restored`, from `backup::adopt_mods::reset_for_adopt`: a backup carries the row and none of the mod's files, which are per computer, so a restore onto another computer owes them; nothing is written for a store without the row, and a join of a shared vault writes nothing); only the migrations and this restore step write a marker. `mark_restored` loops over every pilot, so it writes the Pinboard's marker, `mods_autoinstall_pinboard`, for a restored store that holds a signed, catalogue-installed `atlas.pinboard` row (migration v62 writes the same marker for a store that used the Pinboard, so a restore of one that already moved gets the mod's files back through it; whether the board comes back too is the re-arm below); PM acts only on a marker, removes it in the same transaction that installs the mod (or finds it installed, or puts back the files of a row a restore brought: the pinned version and file, hash-checked) and hands the feature's settings over once per vault (not again when `mods_pilot_landed_<pilot>` is already there), and a `.pmbackup` carries it verbatim, so a backup taken before the install installs the mod again on restore. `mods_pilot_landed_<pilot>` (`"1"`, kept): the install landed here, which each device's page reads once to run its own sidebar rule (the device's own record of having run it is `localStorage` `pm.mods.pilotHandled`). `mods_adopt_map_prefs` (`"1"` until cleared): the Map's per-device view prefs (`pm.map.*`, in `localStorage`) are still on the device that did the install; the page hands them to the mod's `settings` key (`adopt_map_prefs`, writer only, once per vault, only into fields the mod doesn't hold yet) and keeps its own keys, because the mod's storage is per vault and each other vault on the device is owed them too. The Map's handover also deletes the core Map's rows `map`, `doc_layout_meta` and `project_layout_cache` after the mod's `settings` key (content, revision 1, `nodeCap` and, when the core's t-SNE was switched off, `enhanced:false`) is written and read back. The Pinboard's move into its mod (`mods/pinboard_move.rs`; migration v62 writes the first two keys below for a store that used the Pinboard, and a restore's re-arm writes the pending key again) keeps these `settings` keys, all `Truth` about where the person's board lives and each carried verbatim by a `.pmbackup`: `mods_autoinstall_pinboard` (`"1"`, the pilot marker of the Pinboard, read by `autoinstall` like the Map's and removed in the install's transaction), `pinboard_move_pending` (v62's "a non-blank board exists and its copy is owed", or the restore re-arm's; the move deletes it, and the install does nothing about the board while it is absent), `pinboard_moved_sha` (the hex SHA-256 of the legacy row's bytes at the move: the board now lives in the mod, and the legacy row is a frozen snapshot. Read by `projects::pinboard_move_recorded`, which stops a rename or a delete rewriting the legacy row, and by the Calendar's read path below), `pinboard_move_conflict` (the legacy row's SHA-256 when the mod already held a board with content and both were kept; "Use my old board" acts only on a row whose bytes still match it, and either button deletes the key), `pinboard_move_repaired` (`"1"`: the mod's copy has lone surrogate escapes replaced by U+FFFD while the legacy bytes are unchanged; "OK" deletes the key), `pinboard_move_restored` (`"1"`: a restore owes the copy again, so the strip says the board is the one from when it moved, without later edits; written by the re-arm, shown only after the copy has landed and never beside a conflict, deleted by its "OK", and by the move itself if it meets a board the person already made in the mod), `mods_pilot_landed_pinboard` (`"1"`, kept: the install landed here, read once by each device's page for its sidebar rule, like the Map's) and `mods_adopt_pinboard_prefs` (`"1"` until cleared: the Pinboard's three per-device nags, `localStorage`, are still on the device that did the install; the page hands them to the mod's `prefs` key, only into fields the mod does not hold yet, and keeps its own keys). `mod_kv` rows of `atlas.pinboard`, all class `content` (truth, in a `.pmbackup` unless "Also save mod data in my backups" is off): `board` (the board, the legacy row's bytes copied unchanged, or a repaired copy, then the mod's own), `prefs` (the three nags) and `board-before-move` (the mod's own board, copied there once by "Use my old board" before the old one replaces it, and never overwritten). The move's own copy of the board is byte for byte, but PM's mod storage writes object keys in sorted order, so after the mod's first save its `board` equals the legacy row in value, not in bytes: compare structurally. **The restore re-arm** (`autoinstall::rearm_pinboard`, in `reset_for_adopt`, I-32 and I-36): a backup taken with "Also save mod data in my backups" off holds the legacy row and the move's record but no `board`, so when the move is recorded, the legacy row is a board the move can copy, the mod holds no `board` and the signed `atlas.pinboard` row is there, the restore inserts `pinboard_move_pending` and `pinboard_move_restored` and deletes `pinboard_moved_sha`, `pinboard_move_conflict` and `pinboard_move_repaired`, and the normal pass copies the snapshot back in; it deletes no board. **The Calendar's Pinboard dots** (`calendar_pinboard_entries`, `pinboard_legacy::calendar_entries`) have two sources and one rule: while `pinboard_moved_sha` is absent they are derived from `settings['pinboard']` (the freeform timelines' dated entries); once it is there they are the mod's `mod_overlay` rows (derived, rebuilt by the mod at every start and seeded by the move), and an empty table means no dots, never a fallback to the legacy row. Both go through `clamp_overlay`, so a dot a hostile row could add is bounded the same way. **The legacy row `settings['pinboard']` is never deleted by any of this**: the move copies, the old row stays as a frozen snapshot, and clearing it is a later change of its own. **There is no key-prefix convention today** — see Open decisions. |

| `mods` | truth | The installed mods, one row each: version, publisher pin (tier, author, source repo and commit), signed or not, an install id (random, minted by each fresh install, kept by an update or a repair), where it came from, the package's own sha256, the verified manifest and file list (so a mod is rebuilt at startup from the row, never from what the disk claims), state and why, consent (D17), the AI cap with this month's settled spend, the notify day counter and the manifest's `projectRefs`. **The DB is the only home**, travelling in a `.pmbackup` verbatim; the files are not in it. Cascades from `mods`. |

| `mod_ledger` | truth | Gift attribution: which mod made a task or milestone ("made by X"), by mod id and display name as plain text with no FK to `mods`, so it outlives an uninstall and a reinstall can edit its own again. Each row also keeps who the maker was (its publisher pin, whether it was signed, and its install id), because its `mods` row goes at uninstall. A gift is a mod's own (`mods::policy::made_it`) when the id and signedness match its installed row and then, for a signed maker, the pin (so a reinstall edits it again), or, for an unsigned maker, whose pin is only what its manifest claimed, the install id: neither another publisher's mod nor an unsigned file copying a removed mod's id and pin can edit it. Exactly one target per row (a nullable FK to `tasks` or `project_milestones`), cascading only from that target. In a copy that leaves (every backup and the export, `backup::strip`), a developer's folder test mod's rows keep their gift, made by "a test mod": its id, author and source repo are blanked (unpublished work, and an id no install can match). So are the rows of every unsigned mod that is no longer installed: uninstall keeps the ledger and the row has no column for how it was installed, so an unsigned mod is treated as a test mod (a gift of an uninstalled unsigned file mod reads "a test mod" in a copy that leaves too). Signed mods' rows stay. |

Vault-scoped: anyone who can open the vault (a shared vault's co-user included) can read them. **Stripped from every backup snapshot and from the export** (D4: every copy of the store leaves through `backup::strip::snapshot_for_leaving`, which deletes them on the copy, then `VACUUM`s it), so after a restore the user re-enters them, as with keychain credentials. A restore's commit also deletes every row (`backup::adopt_mods::reset_for_adopt`: a row in a restored store was planted); joining a shared vault leaves them, they are the vault's own. A row counts only while its host and header equal the installed manifest's slot (`mods::secrets::read_for_use`), and an approved update or repair that moves or drops a slot deletes the row in its own transaction. Never on the dev inspector's allow-list. Cascades from `mods`. |
| `mod_overlay` | derived | Calendar overlay entries (`{mod_id, id, date, label}`) a mod publishes, which PM draws without running mod code (the pop-out Calendar and the Runway included, D16). The mod re-publishes them from its own content storage when it runs. Cascades from `mods`. Not part of the strip: it is calendar data in a core table, derived and carrying nothing private, so a backup keeps it whether or not "Also save mod data" is on. |
| `mcp_clients` | device | Connected MCP apps: name, the token's hash (the token is shown once and never stored) and scopes. Joining a shared vault leaves them: they are the vault's other devices' apps, and each is bound to the device that issued it by a pairing in that device's own file (`data_dir/mods-mcp.json`, below): a row verifies only when this device holds its pair (the token's hash) AND the row's scopes still hash to the pairing's `scopes_hash`, so a joiner never accepts another device's clients and a shared-store writer cannot widen what an app may read (`mods::mcp::clients::verify`). |
| `ai_reservations` | derived | In-flight worst-case AI cost per mod, held while a call runs: settling deletes the row and adds the real cost to `mods.ai_spent_usd` in one transaction. Usually empty, but not rebuildable: a reservation a crash left behind keeps counting toward the month's cap until the month rolls (`mods/ai.rs`, so a crash cannot be a way to unspend), and dropping the table would lift a cap early. Cascades from `mods`. |

## Checklist for a PR that adds a table

1. Add a row to the register above with a class. `just sync-set` fails without it.
2. If the class is **truth**, say where the portable copy lives. If the answer is "nowhere yet",
   write that in Notes — an honest gap is checkable; an unstated one is not.
3. If the class is **derived**, name the rebuild path, and flag it if re-deriving costs a model call.
4. If the class is **mixed**, name the split by column or key prefix. Do not leave it implied.
5. If the table has an FK to `entities`, also do the three things in INVARIANTS.md I-06.

## Open decisions

These are product calls, recorded here so they are decided once rather than re-litigated per
feature. None is implied by the classifications above.

1. **Export format per truth table.** The recommendation is to extend the existing pattern rather
   than invent a wire format: an encrypted sidecar file at the vault root, per truth domain, as
   `entities.pmrules` and `.pmindex` already do. It survives a vault copy, it is covered by the
   rekey path, and it needs no server.
2. **`preferences` has no portable mirror.** It is truth, the DB is its only home, and its own
   migration assumed the DB travels with the vault. This is the first gap to close, and the
   `.pmrules` shape fits it directly.
3. **Billable re-derivation.** Chat summaries, review proposals and photo OCR are all derived but
   cost money to rebuild. Carry them, or accept the re-bill on a new device?
4. **Frontend `localStorage`** — **RESOLVED (3.114.0-alpha).** The slice that was never a decision
   is now one. Three keys held user content — a milestone sort map keyed by project name, a
   hidden-calendar set of ids that are routinely email addresses, and one dynamically-named
   dismissal key per cloud account — and they moved into the encrypted `settings` table
   (`milestone_ui`, `calendar_ui`, `backup_ui`), so they are encrypted at rest, travel in a
   `.pmbackup`, and go away with PM's data. Everything left is genuine chrome and stays device-local
   **on purpose**: theme, accent and depth per machine is the right default for a display
   preference, and so are panel sizes and view modes. The remaining question is narrower than the
   original one — whether the appearance axes should *optionally* follow the user across machines —
   and it is a product call, not a correctness gap.
5. **`usage_log` aggregation.** Device-local is right for the rows; whether a combined spend total
   across devices is wanted is a separate question.
